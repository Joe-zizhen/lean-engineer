# 实现纪律

## 适用与职责

本文件拥有方案阶梯的操作约束、实现纪律和编码不变量。进入代码实施前必须读取本文件；动作范围和基础读取组合由 [主技能的基础读取](../SKILL.md#基础读取) 统一定义。纯只读 Review 不加载本文件。

系统、宿主、用户和项目指令按既有优先级执行。项目有更严格要求时，合并相同检查并保留更严格要求。

方案阶梯改写自 ponytail（MIT），署名见 [NOTICE](../NOTICE)。

## 方案阶梯

先理解改动触及的代码和真实调用链，再选择方案。按顺序选择第一个能够满足真实需求的方案。两个方案同时成立时，选择靠前的方案。

1. **不需要实现时，不写。** 投机性需求不写代码。说明不写的理由，不伪造 diff 或证据。
2. **项目已有能力可以复用时，复用。** 按 [能力库](reusable-capabilities.md) 先查索引，再读源码并验证调用。实现功能或修改已收录能力时，执行收录和索引同步规则。
3. **标准库可以完成时，使用标准库。** 两个方案成本接近时，选择边界行为正确的方案。
4. **原生平台可以完成时，使用原生能力。** 原生输入、CSS 和数据库约束优先于自定义实现。
5. **已安装依赖可以完成时，按实际版本使用。** 先检查 manifest、lockfile 和项目用法。是否使用过 API，以本仓库的真实调用为准。依赖声明、导入语句或模型记忆不能代替调用证据。本仓库未使用过的 API 必须核对所用版本的官方资料，并通过真实调用验证。文档中存在 API 不等于调用成功。
6. **成熟专项库明显更省时，先评估再引入。** 需要选库时，实际检索包注册表、GitHub 或官方资料，比较候选的维护、兼容、许可证、传递依赖和移除成本。不得仅凭模型记忆断言没有可用方案。检索受限时说明范围，不声称已穷尽候选。首次接入 API 的版本核验与真实调用要求同第 5 项。新增依赖必须服从项目授权。几行代码能够完成时，不为此新增依赖。
7. **否则写清楚、易验证的最小实现。** 最小体现在职责、状态、依赖和分支，不以物理行数衡量。不要为压缩行数而使用难懂的缩写或合并不相关的表达式。单用途代码不造通用抽象。

用户要求更简方案时，重新检查是否有更早成立的方案。用户已经确认的功能范围应完整实现，不再以极简为由反复建议删减。精简必须保留 [编码不变量](#编码不变量)。已知限制按 [记录与交付边界](#记录与交付边界) 留痕。

### 修复入口

修复应针对根因，不能只掩盖症状。修复前读取完整错误，固定复现，并检查相关调用链与调用方。搜索只是定位手段，不能保证找全动态调用、反射调用或外部调用；无法确认的范围应明确记录。

多个调用方共享同一根因时，在共享处修复，并验证受影响的调用方。根因只在某个调用方时，在该调用方修复，避免改坏其他正常调用方。只修工单点名的症状入口，不能证明其他调用方已经恢复。

多组件故障先在组件边界取证，再以单假设最小验证定位失效层。日志消失不等于修复，增加一层 catch 不等于根因已断。修复后重新运行原始复现，并验证受影响的行为。

对能够稳定自动化复现的逻辑缺陷，补充或复用回归测试。确认原实现因该缺陷失败，修复后通过。需要核对原实现时，使用隔离副本或测试夹具，不回退覆盖当前工作区。无法自动化时，记录可重跑步骤、验证限制和原因，不编造测试记录。

## 实现纪律

### 最小改动与方案判断

- 修改前确认目标文件已有的变更。不得覆盖、回滚或顺手整理用户或其他执行者的工作。遇到重叠修改时，先读懂并保留已有改动，无法兼容时再澄清。
- 一次变更解决一个问题。修复不顺手清理，重构不顺手加功能，新功能不顺手优化旧逻辑。不做无关重构、格式化、清理或死代码删除。
- 同样满足需求和兼容要求时，优先移除导致本次问题的冗余或错误逻辑，再考虑叠加新逻辑。不得以此删除必要保护或清理无关代码。
- 不造投机抽象。单实现接口、单产品工厂和不变值的配置必须有真实需求依据。未证明共性前，允许少量重复。
- 控制新增文件数量，但不得为减少文件而混合职责。
- 清理本次改动产生的未使用 import、变量和函数。无关死代码只报告，不删除。
- 每行改动必须能追溯到本次要求。改动超出最初判断时，重新评估风险和方案。
- 实现前声明影响方案的假设。存在更简单方案时，必须指出。
- 需求和验收明确时，可逆的局部实现选择沿用项目惯例直接推进，不反复确认。已有授权不重复索取。
- 缺失信息或不同解释会影响功能范围、兼容性、授权或数据安全时，先说明具体疑点并澄清。不得用默认选择代替必要决策。

### 失败路径与信任边界

- 正常路径与真实失败路径同时处理。不可能场景不写处理。没有新增失败路径时，说明依据。
- 每项资源必须有明确的释放责任方。默认由申请方释放；允许通过返回值、上下文管理器或项目既有机制明确转交所有权，并约定由谁、在何时关闭或取消。转交完成前的失败由申请方清理，完成后由接收方负责；借用者不得释放仍由其他调用方持有的共享资源。
- 新 API 必须有本次真实调用方。检查旧调用方、旧数据和被省略参数使用的默认值。
- 新增校验、过滤、权限或边界守卫时，必须提供能够触发它的反例或测试。只有依据需求、契约和可达路径证明守卫冗余或不适用时，才删除守卫。测试环境、故障注入或构造方法不足时，保留有需求依据的必要守卫，将对应验证记为 `blocked` 或 `not_run`，说明缺口与补证方法。无法构造输入不等于输入不可能出现，不得因此删除安全措施或把未验证写成通过。
- 拼接 SQL、HTML、路径或命令前，先标明信任边界。接收用户数据时，先标明数据从不可信变为可信的位置。使用安全绑定或符合输出上下文的处理。

### 项目一致性与兼容性

- 匹配项目命名、分层、结构、注释密度和既有用法。没有分层时，不发明 `domain`、`infra` 或 `usecase` 分层壳。
- 不假设依赖可用。先检查项目依赖和实际版本，再按项目既有方式使用。
- 修改接口客户端、编译产物或标记为生成的文件前，先确认生成关系。确认由工具生成时，定位源定义和生成入口，按项目约定修改源头并重新生成，核对产物差异。项目明确维护手工补丁时，沿用该流程。生成工具不可用时记录阻塞，不把只改产物称为持久修复。
- 项目编码和行尾约定优先。项目未定义时，默认 UTF-8 无 BOM 和 LF。使用 `git ls-files --eol` 或项目等价方式确认。编辑器显示不能代替检查。
- 非平凡改动必须回答适用的问题：选择了什么，拒绝了什么，重复运行会怎样，做到一半会怎样，信任边界是什么，旧数据或旧调用方是否受影响，失败如何被看见，代码放在哪一层。只回答适用项，不制造固定表格。

### 记录与交付边界

- 实现取舍要留痕。在满足当前已确认的功能、正确性、安全和性能要求的前提下，选择具有已知上限或限制的简单实现时，在关键代码旁或项目约定位置记录限制、升级触发条件和可行的升级方向。未测量的容量上限不得编造。留痕不能代替对需求变更的确认，也不能豁免必要保护。示例：`# lean: 使用全局锁串行处理。若实测锁争用成为瓶颈，评估分段锁，并验证共享状态的一致性。`
- 注释可以说明契约、单位、边界、外部约束和取舍。不得写无法证实的保证。过期注释必须修正。
- 输出默认简洁。用户要求的报告、审查和证据说明不受固定行数限制。
- 同一检查或同一修复连续失败三次时，停止重试并报告阻塞。
- 为完成当前任务，允许根据项目技术栈和现有版本，自动安装并配置必要的项目级开发与验证工具。已有工具优先复用，安装后实际运行验证。项目明确限制安装时，遵守该限制。全局安装或修改宿主配置须另有用户授权。不得自行修改本 skill 来扩大授权。
- 本次新增项目级开发与验证工具时，沿用项目既有锁定机制固定解析版本，并记录实际运行版本；没有锁定机制时，在项目的安装或运行入口指定明确版本或不可变修订。不得仅用浮动标签、分支或未限定版本的命令作为可重复运行依据，版本记录不代替版本锁定。不为此回溯改造无关依赖或新增第二套版本管理；正常升级后重新验证。

## 编码不变量

以下要求不得因精简而删除：

- 信任边界的输入校验、防数据丢失的错误处理、安全措施、基础无障碍和用户明确要求的能力。
- 真实硬件需要的校准参数。时钟、传感器和其他物理输入需要与其实际误差相匹配的处理。
- 读取类函数默认隐藏软删除、禁用、归档或时间窗数据时，必须在函数签名或契约旁说明默认隐藏什么，以及如何获取全量。
- mock、假数据和降级返回必须从产生到消费保持可检查标记。项目已有标记约定优先。中间层不得丢失标记。
- 永久修复必须有足以选择修复边界的因果说明。活跃事故中的可逆、可观测、可快速回滚止血可以先于根因调查，但不得写成根因修复。
