# 独立审查协议

## 独立性

审查他人产出的审查者可以构成独立方。审查自己的产出时，独立方必须是未参与实现的人或独立 agent。自我检查不得写成独立审查。

**对抗立场：默认这次交付是错的，工作是让错误现形。**

这是证伪的工作假设，不是预设审查结论。不得编造问题或放大严重度。证据不支持发现时，零发现是有效结果。

宿主提供 `lean-reviewer` 时，使用该 agent。宿主不支持独立 agent 且没有其他独立方时，记录 `independent_review=blocked`。具备条件但尚未执行时记录 `not_run`。用户验收可以作为独立审查，但必须保留事实记录。

多模型审查可以增加观点差异。它不是独立性的必要条件，也不是正确性的证明。

## 输入与边界

实现者可以编写和运行测试，但不得把自写测试或自我审查称为独立验证。厚审大改及风险分档定义的高后果变更、兼容性增补，其独立审查必须由未参与实现的人或 agent 执行。

向独立方提供 diff、基线、必要代码上下文、规范来源、需求与验收口径、明确非目标，以及已有验证的实际输出。不要提供实现推理、自评或期望结论。

独立方必须自行核对完整变更集。使用 `git status` 和 `git diff`，或者使用文件清单、哈希与副本对比。未跟踪文件也必须纳入。材料与实际变更集不一致时，先报告不一致，不得声称覆盖完整。

独立方应根据需求、合同、固定夹具或独立样例提出测试场景和期望值。重点检查需求理解、边界条件、反例和业务关键路径。实现代码可以用于确定测试入口和覆盖位置，不得用于反推期望值。

只读独立方交付测试场景、期望值和审查意见。主 agent 或授权人员实现并运行测试。独立方再核对真实输出。没有独立方时，记录 `independent_review=blocked`。

审查者的任务是寻找反例和缺失证据，不是证明实现正确。审查者默认只读。审查者不得修复实现后再宣称原修复通过独立审查。实现者修复后，独立方必须复验。

## 领域路由

涉及安全保护或可信路径变化、共享改动可能影响安全边界，或用户要求核对安全修复回归时，组合读取 [安全差异审查](security-diff-review.md)。它细化历史对照、必要传递路径和候选反证，沿用本协议的独立性与发现处置，不替代命中的领域专题。

前端、后端和专项方法都使用包内流程。工具未运行时，记录未运行的检查。不要用通用审查冒充工具验证结果。

## 审查内容

1. 需求轴：逐项检查漏做、多做和错误理解。
2. 规范轴：检查项目规则、合同和本包要求。
3. 安全轴：检查本次实际触及的信任边界。
4. 证据轴：检查测试期望值来源、反例、测试是否能失败、运行结果是否支持结论、未运行项是否被隐藏。

每个发现包含稳定 ID、来源分类、位置、实际结果、预期结果、影响、证据、严重度、置信度、修复建议和复验方法。来源分类为 `introduced`、`pre_existing` 或 `origin_unknown`。既有问题不得算作本次改动的回归。无法根据基线判定来源时使用 `origin_unknown`，不得推测。推断风险必须标为待验证。没有证据的问题不得写成已确认事故。

## 候选发现确认与降噪

1. 将候选发现生成与发布前核验分开。对每个候选主动寻找反证，并核对需求、实际代码路径、触发条件和影响。证据不足时保留为待验证，不得为了产生发现而提高置信度。
2. 缺陷审查默认不发布纯风格、个人偏好或与本次目标无关的清理项。诊断和可观测性发现按实际影响判断，不得按类别一律过滤。用户要求完整质量审查时，非缺陷建议单独分组，不计入缺陷数。
3. 多 agent 或多模型投票只能决定候选是否进入进一步核验，不得替代位置、反例和实际证据，也不得提高置信度。
4. 审查摘要先给出缺陷计数。零发现时明确写为零，并继续报告覆盖和未知项。

## 复审输入与历史缺失

首轮审查没有上一轮历史时，将 `history_consistency` 记为 `not_applicable` 并记录原因。首轮由审查者为发现分配稳定 ID。

后续复审除常规输入外，必须提供：

1. 上一轮完整审查报告和原发现清单。清单包含稳定 ID、状态、处置理由、来源分类、位置、根因和修复机制。
2. 原基线、当前基线、范围变化、自上一轮以来的新 diff，以及修复和验证的实际输出。
3. 当前轮次和轮次上限。非默认上限必须在当前审查前由用户或项目授权，并记录授权者和取值。没有授权记录时使用默认三轮。

独立方必须输出 `history_consistency`：

- 历史完整且一致时为 `passed`。
- 历史材料互相冲突时为 `failed`。
- 必要历史缺失时为 `blocked`。
- 具备材料但未核对时为 `not_run`。
- 只有首轮审查可以为 `not_applicable`。

历史缺失或冲突时，可以执行本次要求的只读审查或修复。`history_consistency` 不是 `passed` 时，不得声称无重复、无静默丢弃或已经收敛。轮次无法确认时记录 `round=unknown`，不得自行重置轮次。需要重新开始时，必须由用户或授权人员明确批准，并记录新首轮和可得的旧 ID 映射。

## 复审与收敛

1. 首轮审查记录基线和范围。每次审查计为一轮，首轮计为第 1 轮。后续复审检查新 diff、原发现以及受影响的调用链和合同。风险范围扩大时，重新扩大审查范围。新提交或基线变化后，不得未经核对沿用旧结论。
2. 稳定 ID 不得只由行号派生。同一根因且同一修复机制的发现合并为一个缺陷类别，并列出全部受影响位置。影响或修复机制不同的发现可以分开。合并或拆分发现时保留旧 ID 映射，不得静默删除旧 ID。
3. 已发布的发现不得作为新发现重复发布。原发现未解决时保留原状态和 ID。出现新证据时更新原发现。复审不得静默丢弃发现。
4. 修复或验收任务结束时，每个发现必须记录 `resolved`、`accepted_risk` 或 `dismissed`。风险接受和驳回必须记录理由，风险接受由授权人员决定。无法完成处置时保留未决状态并记录原因，交付不得写成 `verified`。只读审查可以保留 `open`，不得写成已修复。
5. 默认最多进行三轮审查。第 3 轮审查完成后仍有需要继续修复的未决发现时，停止自动修复和复审，报告未决发现，并请作者重新评估方案或交由授权人员处理。项目或用户可以在审查前规定不同上限。达到轮次上限不等于审查通过。不得为降低轮次丢弃真实发现或降低严重度。
6. 复审轮次上限与实现纪律中的同一检查或修复连续失败停止规则分别执行，互不替代。

## 规则回流

1. 项目已有审查说明时，将其纳入规范来源并检查实际遵循情况。项目没有审查说明时，继续依据项目现有规范、合同和本协议审查，不得把缺少说明等同于没有约束。不要固定要求 `REVIEW.md`，不得为了本次审查擅自新建规则文件。
2. 同一有效意见重复出现时，先确认不是误报，再经用户或项目授权转为 lint、测试、项目规范或审查说明。只读审查者只提出回流建议，不直接修改项目规则。重复误报必须修正审查规则或评估依据，不得只重复关闭。
3. 需要长期复用审查规则时，优先写入项目已有规范文件，或按项目文档放置规则创建。项目没有审查说明且没有文档放置规则时，经用户或项目授权后在项目根目录创建 `REVIEW.md`。未获授权时只在交接中提出建议，不创建文件。`REVIEW.md` 是兜底位置，不是所有项目的强制文件名。
4. 审查说明声明的跳过路径必须列入未检查范围，不得计为通过。

## 结论边界

分别报告审查覆盖、检查发现、验证状态和发布条件。台账结构通过不等于证据真实。独立审查完成不等于需求正确。风险接受和发布由授权人员决定。
