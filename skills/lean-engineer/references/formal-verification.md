# 形式化验证

## 何时使用

先写出一个可判定的性质。无法写出性质时，不建立形式化模型。

适合的情况：

- 多个事件顺序会破坏业务不变量。
- 重试、超时、取消或恢复会产生隐藏状态。
- 解析器、内存安全或数据结构需要输入边界保证。
- 普通测试难以覆盖关键反例。

普通测试已经能低成本覆盖时，使用普通测试。

## 工具选择

让问题决定工具：

- 事件交错和状态转移使用模型检查器。TLA+ 与 TLC 是默认候选。
- 代码级输入性质使用能够直接分析该语言的验证器。
- 无界性质需要证明或其他能够表达该性质的工具。

使用项目已经配置的 TLA+、TLC 或其他模型检查器运行验证。本包提供性质、模型、代码映射和反例重放流程，不包含模型检查器运行时。没有可用运行时时，记录 `formal_verification=not_run`。不得擅自下载 Java、TLC 或其他运行时。手工状态图只用于沟通，不得冒充模型检查通过。

## 项目本地验证资产

形式化验证必须绑定具体项目。通用示例不能证明项目代码。

每个验证资产必须包含：

1. 用业务语言写的性质及其失效后果。
2. 模型、验证器输入、配置和固定工具版本。
3. 模型变量、原子动作与代码文件及行位置的映射。
4. 状态边界、输入边界、假设和明确省略项。
5. 一条可重复运行的命令。
6. 覆盖的代码文件和最近同步的基线。

将可重复命令接入项目验证入口或 CI。运行时、模型、配置和命令必须与当前基线一起记录。只读审查者核对实际输出，不要求获得执行权限。没有运行时时仍为 `formal_verification=not_run`。模型文档和手工状态图不能作为模型检查通过的证据。

代码变化影响已覆盖区域时，先确认模型仍描述代码。不得只更新同步基线。

## 反例与通过边界

- 每个性质都必须在已知破坏变体上失败一次。随后恢复原状并重新检查。
- 模型发现违规后，使用真实入口重放反例。只断言用户、客户端或其他系统组件可观察的结果。
- 设计尚无代码时，模型反例就是当前证据。交付时必须说明没有代码可重放。
- 模型通过只覆盖声明的模型与边界。代码映射未确认时，不得写成代码已证明。
- 不得通过弱化性质、删除状态或隐藏反例来制造通过。

交付给出性质、工具、边界、命令、结果、反例、代码重放状态和未覆盖项。
