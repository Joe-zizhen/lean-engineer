# 交付与运行

## 检查对象

列出环境配置、构建产物、部署顺序、功能开关、日志、指标、追踪、告警、资源限制、备份和恢复。区分开发、预览、测试和生产基线。

## 必须成立的不变量

- 必需配置在启动时校验。默认值不会意外开放管理、调试或敏感能力。
- 日志、指标和追踪能够定位真实失败，并且不记录秘密或不必要的个人信息。
- 告警对应可执行的处置。监控没有数据不等于系统没有故障。
- 新旧服务、任务、消息和数据库在部署与回滚窗口内保持兼容。
- 就绪与存活检查表达不同事实。停止接收流量后，在途任务具有确定的完成或恢复路径。
- 回滚覆盖代码、配置、数据、消息和外部副作用。平台提供回滚按钮不等于应用能够恢复。

## 必造反例

- 缺少必需配置、配置指向错误环境或旧配置遇到新代码。
- 新旧 producer 与 consumer 混跑，旧 worker 收到新消息。
- 在部署、回滚、实例终止和依赖中断期间处理请求。
- 监控或日志后端不可用，主业务仍按定义降级。
- 从备份恢复后再次处理旧消息或重复任务。

## 性能与容量

主要任务是性能或容量时，执行以下包内流程：

1. 确定本次 diff 或完整审查的范围。建立工作负载，包括入口流量、数据量、并发、资源限制和业务目标。未知项记为 `unknown`，不得用假设代替事实。
2. 从真实入口建立关键路径和资源清单。包含下游调用、数据库、缓存、消息、连接池、CPU、内存和 IO。
3. 先收集源码、配置、指标、追踪、性能分析、查询计划和负载测试证据。所有数字必须来自测量、配置、用户输入或明确推导。不得编造 p99、命中率、查询计划或扩展倍数。
4. 每个发现必须记录位置、瓶颈机制、证据、工作负载条件、影响、反证、置信度、建议、取舍和复验方法。复验方法必须包含能够推翻该发现的观察或测量。不得用通用最佳实践替代瓶颈机制。
5. 优化前后必须在相同工作负载、构建、数据量和环境下测量。没有测量时，不得声称更快、更省或已经解决性能问题。未经授权不得对生产目标压测或探测。

## 证据与复验

使用生产等价的构建和配置。演练部署、回滚、恢复和关键告警。无法访问生产环境时，保留对应 `blocked`，不得写“生产已验证”。

复验核心链路、旧新兼容、监控证据和恢复结果。发布决策由授权人员作出。
