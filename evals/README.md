# 审查器评估协议

## 评估边界

`tasks.json` 定义 skill 触发、引用路由和禁止声明。它不能测量代码缺陷检出率、误报率或有害建议率。

本文件定义真实审查行为评估的案例、运行和指标口径。本文件不提供模型运行器。真实事故案例集和实际执行状态以相应案例数据、`runs.json` 和带日期的 `VALIDATION.md` 为准。评估协议存在不等于评估已经完成。

## 规则试用与效果对照

把路由与执行试用、真实缺陷评估分开。用人工构造的小项目检查查库、导入、首次收录、索引更新和阻塞处置时，记录为 `kind=routing`，并标注合成夹具。它证明该次模型执行的行为，不证明真实事故检出率。

规则试用至少包含以下场景：已有能力直接复用、首次实现后收录、沿用项目现有目录、只读任务不写入、索引与源码失配、必要守卫缺少验证条件、高后果条件修改、普通小改。评估实际文件、工具记录和调用结果，不能只看最终声明。

需要比较效果时，在同一固定案例集上分别运行不加载本 skill、旧版本和新版本。保持模型、工具权限、任务输入、源码基线与资源预算一致。每次使用独立上下文和独立副本，不向执行者提供答案、预期发现或前一次结论。模型或预算无法确认一致时，报告差异，不给出因果改善结论。

运行前固定案例标注、成功条件、重复次数和匹配规则。保存模型可见输入、实际读取与操作记录、输出、产物及评判依据。不要把一次正确回答当作稳定表现。

同时记录任务成功率、重复实现、错误复用、索引失配、无关改动、耗时和可取得的工具调用数与 token 用量。无法取得的计量记为未知，不能估算成实测值。真实缺陷指标仍按下文定义计算。

真实项目案例或运行条件不足时，先执行可运行的规则试用，并列出剩余缺口。不得生成虚构的运行记录，也不得把合成夹具作为真实事故案例。

## 案例来源与标注

1. 缺陷案例来自真实事故、回退、前向修复或经过确认的代码缺陷。保留对应基线、变更和修复证据。
2. 熟悉相关代码的授权人员确认缺陷位置、失效机制、预期行为和影响。存在未解决分歧的案例不得作为已标注缺陷。
3. 干净变更案例由授权人员在声明范围内确认没有已标注缺陷。干净只表示该范围没有已标注缺陷，不表示系统没有缺陷。
4. 每个案例记录稳定 ID、来源、基线、变更、已标注缺陷、干净标记、故意行为、非目标、标注人员和证据。秘密与个人信息必须脱敏。
5. 在运行前记录审查发现与已标注缺陷的匹配规则。不得在看见模型输出后改变匹配规则。
6. 作者修复、评论关闭或线程解决只表示处置结果。它们不能单独证明发现是真阳性。

## 运行触发与记录

1. 修改审查提示词、工具或模型后，在同一完整评估集上重新运行。保留变更前后结果。
2. 新事故或回退完成标注后，加入后续评估集。比较结果时区分固定回归集与新增案例。
3. 只有项目已经具备自动评估设施时，才使用每日运行。不得把每日运行声明写成已经建立的调度。
4. 每次真实模型执行都必须写入 [runs.json](runs.json)。`tasks.json` 只保存路由定义和运行计数，不保存模型输出。
5. 每个运行记录包含 `id`、`kind`、`model`、`prompt_version`、`tool_version`、`case_set_version`、`executed_at`、`output_locator` 和 `output_sha256`。`kind` 为 `routing` 或 `review_behavior`。时间必须包含时区。
6. `output_locator` 必须指向 `evals/evidence/` 下的包内文件。证据包含实际输出和对应的计算结果。证据必须脱敏。`output_sha256` 是该文件内容的 SHA-256。证据路径不得包含符号链接、目录联接（junction）或其他 Windows 重解析点（reparse point）。
7. `tasks.json` 的 `model_runs` 必须等于 `runs.json` 中有效运行记录的数量。静态校验和单元测试不得增加该计数。没有实际输出时不得添加运行记录。
8. 包校验器只检查运行记录结构、计数、证据存在性和证据哈希。它不能认证模型输出、指标或标注是否真实。

## 指标

- `defect_recall`：按运行前匹配规则检出的已标注缺陷数，除以已标注缺陷总数。
- `finding_precision`：经标注人员或独立证据确认的真阳性发现数，除以审查报告的发现总数。
- `harmful_clean_case_rate`：至少包含一条会导致有害修改建议的干净案例数，除以干净案例总数。
- `duplicate_finding_rate`：经确认属于重复发布的发现数，除以审查报告的发现总数。
- `rounds_to_pass`：从首轮审查到全部必需发现达到处置条件所需的审查轮次数。首轮计为第 1 轮。分别报告中位数和 95 分位数。
- `cap_reached_rate`：达到审查轮次上限时仍有未决发现的案例数，除以全部已结束案例数。

所有指标只统计已结束运行的案例。尚未结束运行的案例单独记录，不得进入已完成案例指标。任一指标的分母为零时，将该项记为 `not_applicable`，不得记为 0 或 100%。`rounds_to_pass` 只统计达到处置条件的案例。达到轮次上限且未达到处置条件的案例必须计入 `cap_reached_rate`，不得从结果中删除。

团队具备发布遥测时，可以另行记录人工审查时间、人工等待时间、回退率和事故率。这些指标不能由静态测试或路由评估代替。

## 结果判定

1. 优先检查真实缺陷召回和有害建议，再检查审查轮次。不得通过丢弃真实发现降低轮次。
2. 不用单一综合分隐藏召回、误报或有害建议的退化。逐项报告前后差异和未知项。
3. 没有真实案例和实际模型输出时，不得宣称检出率、误报率、审查轮次或发布结果已经改善。
4. `expected_references` 是案例必须读取的最低集合，不是允许读取的上限。评估必须核对实际读取文件，不能只检查最终回答。
