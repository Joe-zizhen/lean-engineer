# 验证与证据

## 证据类型

| 类型 | 可以证明 | 不能单独证明 |
| --- | --- | --- |
| `specification` | 需求、合同或预期是什么 | 实现满足预期 |
| `source` | 当前源码包含或不包含某个结构 | 真实运行全部正确 |
| `test` | 指定测试在指定环境得到指定结果 | 未覆盖场景正确 |
| `runtime` | 真实入口的可观察行为 | 未操作路径和隐藏副作用 |
| `measurement` | 指定条件下的数值 | 其他负载、设备或数据量下的数值 |
| `model` | 指定模型和边界内的性质 | 实际代码与模型等价 |

证据必须包含位置、命令或观察步骤、环境、时间和结果。秘密与个人信息必须脱敏。

## 领域证据与台账范围

这些领域的局部任务默认检查本次改动和受影响调用链。用户要求完整审查时，先建立声明范围内的对象与检查项清单，记录总数、已查数、未查数及原因，不得静默缩成 diff 审查或仅凭几个样例宣称完整。

证据种类描述证明方式，不限定技术栈。真机操作日志属于 `runtime`；自动设备测试或数据断言属于 `test`；波形、功耗、时序、吞吐量和数据差异统计属于 `measurement`。按证据实际内容分类，不因附件名或格式自动认定充分。

除通用字段外，记录决定复现结果的条件：移动端的 OS、机型、应用版本与权限；硬件的板卡版本、固件构建、探测点、采样与负载；数据任务的输入快照、分区、时间窗口、口径版本与运行 ID。结论应关联原始记录和预期来源，不能只保留“通过”的摘要。

内置 `validate_review.py` 和 JSON 模板仅校验后端六专题。需要其他领域时，沿用项目已有台账；没有时，以精简表格记录：检查对象、风险或不变量、操作与预期、实际结果、证据位置与基线、状态、未查范围。不得将新领域硬塞进后端专题来声称完整覆盖。

同一交付若同时含后端台账和领域补充记录，合并所有必需检查后按下方规则判定状态。任一领域的失败、阻塞或未运行都会影响整体结论；后端脚本的 `release_ready` 不能替代该汇总。领域记录中的必需检查和“不适用”依据须由项目要求与实际改动确定，不得为取得通过而删项。

## 检查状态

- `passed`：所需证据支持该检查的预期。
- `failed`：证据表明实际结果违反预期。
- `blocked`：缺少环境、权限、数据、合同或工具，无法执行。
- `not_run`：具备执行条件但本次没有执行，或者尚未尝试。
- `not_applicable`：有具体依据证明该检查不在范围内。

`blocked` 和 `not_run` 都不是通过。`not_applicable` 不能替代无法验证。

交付状态只有三类：

- `verified`：所有必需检查均为 `passed` 或有依据的 `not_applicable`。
- `partial`：存在 `blocked` 或 `not_run`，且没有必需检查失败。
- `failed`：任一必需检查为 `failed`。

不得把 `partial` 写成完成验收。不得把检查计划写成检查证据。

## 测试与质量门

1. 优先使用项目已有构建、静态检查、测试和运行入口。
2. 测试期望值必须记录来源。来源可以是用户要求、合同、固定夹具、独立样例或可审查的业务规则。不得从被测实现反推同一答案。厚审大改的关键测试缺少独立依据时，对应检查为 `blocked`，不得使用 `verified`。
3. 实现者可以编写测试。厚审大改、高后果变更和兼容性增补仍需独立方核对期望值来源、需求、反例和验证充分性。独立性来自依据和审查，不要求重新编写全部测试。
4. 新增或修改关键契约测试时，使用一个已知破坏验证它能失败。随后恢复并再次运行。保留绿、红、绿的真实记录。
5. 厚审大改必须实际通过复杂度、测试与变异、架构约束三道质量门。三门均为必需检查，交付状态按 [风险分档](risk-gates.md) 判定。
6. 复杂度：对新增或修改函数运行机器检查。项目阈值优先。没有项目阈值时，圈复杂度上限为 10。人工阅读不能替代质量门证据。
7. 测试与变异：相关测试必须通过，变更代码必须实际运行变异测试。非等价变异体必须全部杀死。等价变异体必须单独记录依据。未配置或未运行变异测试时记录 `blocked` 或 `not_run`，不得用覆盖率或手工变异替代通过。
8. 架构约束：使用项目已有的机器规则检查分层、循环依赖、命名和位置边界。没有项目或用户提供的规则时，该门为 `blocked`。不得自行发明规则并宣称通过。
9. 工具安装按 [实现纪律](implementation.md#记录与交付边界) 的项目级工具规则及已有授权执行，不重复索取授权。不得把安装失败写成工具门通过。缺少工具、配置或规则不得写成 `not_applicable`。纯文档或无代码改动确实没有检查对象时，必须记录具体豁免依据。
10. 没有测试基线时，只补本次变更所需的最小测试。不得宣称历史代码已经覆盖。

## 执行前检查与项目交接

本节的预检只覆盖本次风险档位以及用户或项目明确要求的检查。读取本文件或给出验收结论，不自动产生三门建设、工具安装或 CI 改造任务；缺失的必需检查仍按原状态规则处理。只读审查记录现有条件和缺口，不建立或修改工具与 CI。

1. 检查项目 manifest、lockfile、构建脚本、测试配置和 CI 配置。记录判断依据的位置。不得仅凭工具名称或文档声明认定项目已经配置质量门。
2. 本轮需要三道质量门时，分别记录其执行条件：已配置、缺少配置、缺少工具或无法运行。能力预检只描述执行条件，不替代实际质量门结果。
3. 优先运行项目已有的统一命令。记录工具版本、变更范围、命令、结果和证据位置。预检通过不得写成质量门通过。
4. 缺少配置或工具时，给出最小接入方案。已有任务授权覆盖必要项目级工具时，按实现纪律安装、配置并运行；项目明确禁止或超出已有授权时不安装，未完成的必需检查使交付保持 `partial`。未检查项目配置前，不得声称工具不可用。
5. 本轮任务包含 CI 质量门接入或更新，且授权覆盖相应修改时，将同一个项目命令接入 CI。否则复用并报告已有入口，不把接入建议新增为本次必需验收项。用户或项目已明确要求的 CI 检查仍是必需项；缺权限或配置时记录 `blocked`，不得当作完成。PR 可以限定变更范围，定时任务可以运行更大范围，但不得降低通过标准。需要阻止合并时，由项目 CI 必需检查和分支保护执行。不得把 AI 报告写成已经建立合并阻断。
6. 本 skill 定义质量门要求和证据口径，不提供各项目通用的质量门执行器。本地与 CI 证据必须对应同一源码基线，才能共同支持同一结论。

## 行为、性能与恢复

- 可观察改动必须通过真实页面、请求、任务或对应测试观察行为。无法运行时标记 `not_run` 或 `blocked`。
- 性能结论必须有同条件的前后测量。没有测量时不得声称更快或更省。
- 回滚代码不等于恢复数据。持久化、支付、身份和权限变更必须分别说明代码回滚与数据恢复。
- Git 不可用时，使用文件清单、哈希或副本对比。`git diff` 不包含未跟踪文件时，不得把它当作完整变更证明。

## 完成判定

交付前逐条列出用户要求。每项关联至少一个实际结果或一个明确缺口。构建通过、测试通过、台账完整和独立审查分别是不同事实。任何一项都不能单独证明整个需求已经正确实现。
